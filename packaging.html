packaging

“I have made this longer than usual because I have not had time to make it shorter.”
  — Blaise Pascal

a package is a directory in repo/pkgs/. it needs a version and a build script, and that's usually it. if you've written a kiss package, you already know how.

example: packaging yte

get the repository:

$ git clone https://github.com/yagnilinux/repo

make a directory for the package:

$ mkdir repo/pkgs/yte

put the version in repo/pkgs/yte/version:

0.3

put the source url in repo/pkgs/yte/source:

git https://github.com/yagnilinux/yte.git main

write repo/pkgs/yte/build. it compiles yte and installs it into $1:

#!/bin/sh -e
musl-gcc -std=c99 -Os -s -static -o yte yte.c
install -Dm755 yte "$1/usr/bin/yte"

make it executable and build:

$ chmod +x repo/pkgs/yte/build
$ repo/mkrepo

the package is now repo/repo/yte@0.3.tar.gz.

the files

repo/pkgs/<name>/version     the version
repo/pkgs/<name>/build       how to build it
repo/pkgs/<name>/depends     what it needs, one per line, if anything
repo/pkgs/<name>/source      where to get it, if it isn't in the directory
repo/pkgs/<name>/files/      configs and patches, if you have any

build

a shell script that installs the program into $1, as if $1 were /. $PKG is your package's directory, so $PKG/files/ is where your configs and patches are.

build it static (musl-gcc -static) and strip it, so it keeps working whatever else gets upgraded.

source

git <url> <tag>          a git repository
apt-src <pkg>            an ubuntu source package
apt-deb <pkg>...         ubuntu binary packages (firmware only)

your own repository

$ repo/mkrepo      # build every package into repo/repo/
$ repo/mkrootfs    # build an install tarball

bump version whenever you change a package, or nobody gets the change. mkrepo won't let you forget.

put repo/repo/ on any web server and point /etc/jits/repo at it. that's a distribution. want checksums? SUMS=1 repo/mkrepo puts sha256 sums in the index and jits checks every download against them.
